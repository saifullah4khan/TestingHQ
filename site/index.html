Early build, in public

Self-testing tools for intake pipelines.

TestingHQ is a small suite of tools for stress-testing the systems that ingest messy real-world input. The first tool, Blast, generates a spectrum of realistic-to-garbled inbound-email payloads and fires them at an intake endpoint you control, so you can see how your parser behaves under real-world nonsense instead of hand-typed happy-path samples.

Where this stands today: the M0 skeleton is in place. The package installs, the CLI surface and safety guardrails exist and are tested, and CI runs on every change. The generator, transport, reporting, and web UI are being actively built right now. Commands documented below are the real CLI surface, but some paths still print a "not implemented yet" placeholder until that work lands.

What Blast does

Blast generates inbound-email payloads across a spectrum of messiness, from clean and well-formed through typo-ridden, multilingual, and half-gibberish, up to structurally malformed and degenerate. It POSTs them as SendGrid Inbound Parse-shaped payloads to a target endpoint you configure, and reports where the parser choked.

Blast is about variety and correctness: finding the inputs that break extraction, reproducibly. Every run is seeded, so the same seed and configuration produce the same corpus every time, which makes a failure something you can hand to an engineer instead of something that only happened once.

The suite ships as a single installable package, testinghq, with subcommands for each tool: testinghq blast ... today, and testinghq barrage ... once that tool exists.

The messiness spectrum

Real inboxes do not send you clean test fixtures. Blast is designed to generate payloads across five categories, from a well-formed happy path down to input that barely resembles an email at all.

01

Clean

Well-formed, valid email. Correct headers, sensible body, nothing surprising. The happy path.

02

Messy-but-valid

Typos, odd formatting, unusual but legal structure. Still technically valid input a parser should handle without complaint.

03

Multilingual / gibberish

Non-English content, mixed scripts, encoding oddities, and text that degrades toward noise.

04

Structurally malformed

Payloads that break the expected shape: missing fields, malformed multipart structure, inconsistent metadata.

05

Degenerate

Edge-of-void cases: empty bodies, oversized fields, extreme or missing attachments.

This spectrum describes what Blast is built to generate. As noted above, the generator that produces every level of the spectrum is still being built; today the CLI surface and guardrails exist, and the messier levels land in upcoming milestones.

Responsible use

Blast is a fuzzer and self-testing tool for endpoints you control. It POSTs provider-shaped payloads at your own ingest.

It is not an email sender.

  • It does not deliver mail to arbitrary inboxes.
  • It does not use SMTP or any real mail delivery path.
  • It does not try to defeat spam filters.
  • It does not forge sender authentication to fool real recipients.
  • All generated content is synthetic and uses reserved example domains (such as example.com).

Dry-run is the default. Firing requires an explicit --send flag and a target you have declared in configuration. Rate limiting is on by default. Blast will refuse to fire at a target that is not explicitly configured.

Install and quick start

Install the package in editable mode with the dev extras:

pip install -e ".[dev]"

Then generate a corpus and try a dry run:

# generate a corpus to disk, no network
testinghq blast generate --count 100 --seed 1 --out corpus

# dry run by default: shows what it would send, makes no network calls
testinghq blast fire --target local

# actually fire at a configured target (explicit and rate limited)
testinghq blast fire --target local --send

What is real right now

The commands above are the actual argument surface defined in the CLI today: testinghq blast generate, testinghq blast fire (with --target, --seed, --count, and --send), and testinghq blast replay <run>. The dry-run-by-default guardrail is real and tested: fire without --send always reports a dry run and never touches the network. The generator, transport, and reporting behind these commands are still being built, so running them today prints a placeholder message rather than producing output.

Roadmap

TestingHQ ships as one package with subcommands, built one tool at a time.

In progress

Blast

Variety and correctness: proving a parser handles the full spectrum of inbound-email messiness. The CLI, configuration, and safety guardrails are in place and tested. The generator, transport, and reporting are being built now, alongside a web UI over the same engine.

Next, not available

Barrage

Volume and throughput. Where Blast proves a parser is correct under messy input, Barrage is planned to prove a pipeline holds under load. Barrage has not been built yet: no code exists for it today, and it is currently design-stage only.
