Early build, in public

Self-testing tools for intake pipelines.

TestingHQ is a small suite of tools for stress-testing the systems that ingest messy real-world input. The first tool, Blast, generates a spectrum of realistic-to-garbled inbound-email payloads and fires them at an intake endpoint you control, so you can see how your parser behaves under real-world nonsense instead of hand-typed happy-path samples.

Where this stands today: the Blast engine core is built and tested: deterministic corpus generation, the six composable mutators behind every messiness level, seeded attachments, a 20-case named edge-case catalog, SendGrid Inbound Parse-shaped serialization, an injectable HTTP transport, target configuration, rate limiting, and the safety guardrails, backed by a dedicated security test suite. The CLI is wired to that engine: testinghq blast generate, fire, and replay all run, as do the run artifact, expectation-based reporting, and pass/fail assertions. See Install and quick start for exactly what runs today.

What Blast does

Blast generates inbound-email payloads across a spectrum of messiness, from clean and well-formed through typo-ridden, multilingual, and half-gibberish, up to structurally malformed and degenerate, and POSTs them as SendGrid Inbound Parse-shaped payloads to a target endpoint you configure. Blast is about variety and correctness: finding the inputs that break extraction, reproducibly.

Every generated payload is an InboundEmail in memory (subject, text, html, headers, envelope, charsets, attachments, and a ground-truth record of what it was built to say), serialized into the same named multipart fields a real SendGrid Inbound Parse webhook sends in parsed mode: headers, to, from, subject, text, html, envelope, charsets, an attachment count, an attachment-info field when there is at least one attachment, and one file part per attachment. That shape is the default and the only one the CLI sends today: Mailgun, Postmark and raw MIME encoders exist and are tested, and a config key names one, but that key is validated and then ignored, so the wire bytes are SendGrid-shaped whatever it says.

  • Deterministic generation. A seeded generator builds well-formed clean payloads. The same seed and count produce byte-identical output every time; nothing reads the wall clock or unseeded randomness.
  • Six composable mutators. Typo/transposition, homoglyph and mojibake substitution, script mixing, word salad, structural noise (quoted reply chains, forwarded-message headers, broken HTML, signature blocks, and occasional blanking or truncation), and encoding sabotage (a declared charset that does not match how the content was actually encoded). Every messiness level below is a weighted recipe over this one mutator set, not a separate code path.
  • Seeded attachments, where the corpus is built to need them. Ordinary files with correct magic bytes, zero-byte files, oversized files, and deliberately awkward ones (empty, path-traversal-shaped, or reserved-device-name filenames; mismatched or nonsense content types), all reproducible from the same seed. Blast's own corpus attaches none of them: blast generate and blast fire emit clean payloads. The generators are used by verify and ledger, which attach ordinary and zero-byte files, and by three named catalog cases. Oversized attachments are reachable from the Python API only.
  • A named edge-case catalog. 20 individually named, generic payload shapes you can build on demand, independent of the random messiness pipeline: empty subjects, reply-to mismatches, plus-addressing, a header-injection attempt, mixed line endings, many-recipient envelopes, zero-length envelopes, and more.

Firing is built on an injectable HTTP transport with an enforced timeout, target configuration loaded from TOML with environment overrides, a client-side token-bucket rate limiter, and the guardrails described below.

There is also a small local web UI (plain HTML/CSS/JS over Python's stdlib http.server, nothing to build or install) that previews the dry-run and fire flow and an expectation-based results view. It runs the same engine as the CLI, not a fixture stand-in. Its fire path is the one that is not rate limited: keep runs from the browser short, and see docs/SECURITY.md.

The suite ships as a single installable package, testinghq, with a subcommand per tool: blast, barrage, compare, verify, ledger, redeliver, loop, steady, report and config validate. All ten ship.

The messiness spectrum

Real inboxes do not send you clean test fixtures. Blast generates payloads across five categories, from a well-formed happy path down to input that barely resembles an email at all. Every category past "clean" is a weighted recipe of how many times to apply the six mutators described above, not a separately written generator, so the levels compose instead of drifting apart. Percentages below are the fixed mix the CLI draws from; picking categories by hand is a web UI feature.

01 · 20%

Clean

Well-formed, valid email. Correct headers, sensible body, nothing surprising. The happy path, no mutators applied.

02 · 40%

Messy-but-valid

One to three typo passes, plus an optional structural pass (a signature block, a quote chain). Still technically valid input a parser should handle without complaint.

03 · 20%

Multilingual / gibberish

One or two passes each of script mixing and homoglyph/mojibake substitution: foreign-script words spliced in, look-alike characters, wrong-encoding round trips.

04 · 15%

Structurally malformed

One to three structural-noise passes, plus optional encoding sabotage and word salad: broken HTML, mismatched charsets, missing or truncated fields.

05 · 5%

Degenerate

Three to five structural-noise passes stacked with word salad and optional encoding sabotage. Edge-of-void cases: blanked or truncated fields, compounding corruption.

Address fields (to, from, envelope) are never touched by any mutator at any level, including degenerate: corruption is confined to subject, text, html, and charsets, so every generated payload stays on a reserved domain regardless of how garbled the rest of it gets.

Responsible use

Blast is a fuzzer and self-testing tool for endpoints you control. It POSTs provider-shaped payloads at your own ingest.

It is not an email sender.

  • It does not deliver mail to arbitrary inboxes.
  • It does not use SMTP or any real mail delivery path.
  • It does not try to defeat spam filters.
  • It does not forge sender authentication to fool real recipients.
  • All generated content is synthetic and uses reserved example domains (such as example.com).

Dry-run is the default. Firing requires an explicit --send flag and a target you have declared in configuration. Blast refuses to fire at a target that is not explicitly configured, and separately refuses any target that looks like a real, publicly routable host (rather than a reserved domain, localhost, or a private address) even if it is present in configuration. Every address a payload generates is checked against the reserved-domain contract before firing. Rate limiting is on by default.

These guardrails are first-class, not a README promise: they are implemented in one canonical module that both the CLI and the web UI import rather than reimplement, and they are backed by a dedicated security test suite. See docs/SECURITY.md in the repository for the full policy.

Install and quick start

Install the package in editable mode with the dev extras:

pip install -e ".[dev]"

Then generate a corpus and try a dry run:

# generate a corpus to disk, no network
testinghq blast generate --count 100 --seed 1 --out corpus

# dry run by default: shows what it would send, makes no network calls
testinghq blast fire --target local

# actually fire at a configured target (explicit and rate limited)
testinghq blast fire --target local --send

What is real right now

All of it. The commands above are the actual argument surface defined in the CLI: testinghq blast generate, testinghq blast fire (with --target, --seed, --count, --config, --rate, --out, and --send), and testinghq blast replay <run>. Each one runs against the real engine underneath it. generate writes a corpus and a manifest to disk, fire either previews what it would send or posts it, and replay rebuilds the original corpus from a saved run's seed and config and refuses if the recomputed payload hashes do not match the ones the artifact recorded.

A fire run prints an expectation-based summary: how many payloads landed in each response class, how many broke an expectation, and which ones. A clean payload that did not get a 2xx is a failure. A degenerate payload that got a clean 4xx is a pass. That is the product's whole point, and it is what the run artifact records per record.

The local web UI runs the same engine rather than a fixture stand-in. The Tools section below covers the two tools that generate and apply load.

Tools

TestingHQ ships as one package with a subcommand per tool, built one at a time. The two that generate and apply the load are below. The other eight are named in Tools in the README, with what each one checks. Nothing is currently in progress, so there is no roadmap to report.

Shipped

Blast

Variety and correctness: proving a parser handles the full spectrum of inbound-email messiness. Generation, the six mutators and five messiness recipes, attachments, the named catalog, serialization, transport, configuration, rate limiting, guardrails, the run artifact, expectation-based reporting with pass/fail assertions, and byte-identical replay are all built and tested. The local web UI runs the same engine, not a stand-in.

Shipped

Barrage

Volume and throughput. Where Blast proves a parser is correct under messy input, Barrage drives load at a controlled rate. Both firing modes are built, and both dispatch through a pool of --concurrency worker threads, so a target slower than the arrival interval no longer caps the achieved rate below the rate you asked for. Open-loop holds its arrival schedule regardless of target latency, which is the condition a breaking point exists to find. Reports throughput against target, p50/p90/p99 latency, error rate over time, and the knee where the endpoint starts shedding load or slowing; a run that held reports no knee, which is a result rather than a missing value. Writes a run artifact that can be replayed later from its seed and config.
